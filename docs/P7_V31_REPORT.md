| `prop:desk` | 64 | 64 | 128 | |

| `prop:curtain` / `prop:plant_pot` | 30 / 30 | | 60 / 60 | |

**结论（实测，非按代码行数猜）**：

1. 38 件家具合计 **680 mesh / 1360 dc_est**（占全场景 40%），是最大增量；

**因此"减少实例数"是唯一能同时压低 dc 与 CPU 提交成本的手段**，合批方向由此确定。

## 4. 家具、楼梯、栏杆合批的实际变更及效果

### 4.1 实现（新增 `scripts/isle_batch.gd`）

把静态 MeshInstance3D 按 **(空间区间, 材质实例, 顶点属性签名)** 合并成少量"多 surface ArrayMesh"：

- 顶点/法线/切线/UV 的局部→组局部变换由引擎 `SurfaceTool.append_from` 完成；
- **材质对象原样复用（不 copy）**，所以 `next_pass` 描边、`self_lit`、`glow` 全部保留；
- 只合并 `shaders/toon.gdshader` 材质：玻璃/草/海/天空/加色光晕/影子斑一律跳过；
- **一个实例只有在它的全部 surface 都可合并时才参与**，杜绝"合并一半 + 原实例残留"的重复绘制；
- 被合并部件写入 `batch_manifest`（类别/尺寸/变换/材质/三角形数），供探针按部件级复核。

分层接入（刻意不做成"整屋一个巨型网格"）：

| 层级 | 接入点 | 合并前 | 合并后 |
|---|---|---:|---:|
| 每件家具 | `cottage._merge_props_of()`（38 件各自在自己 `Prop_<kind>_<seq>` 节点内） | 680 mesh | 38 mesh / 190 surface |
| 楼梯 | `cottage._stairs()` 末尾 | 99 mesh | 1 mesh / 7 surface |
| 房屋 | `cottage.build()` 末尾，按 `interior` / `attic` / `shell` 三区分组 | 325 mesh | 20 mesh / 73 surface |

动态件用 `no_batch` 契约保护：`DoorPivot`（门扇整体旋转）、`PorchCat`（逐帧待机动画）、
`BowSpot`（船首探照灯昼夜切 visible），以及 `DoorArch` / `DoorSpandrel` 两个具名关键结构件
（合批收益仅 2 个 pass，换可调试性）。

### 4.4 已评估但**不实施**的优化：小船合批

小船整船是刚体（所有部件挂 `Sailboat` 根或其 6 个具名分组下，相对变换不变），
技术上可合批，实测可把 **127 mesh / 238 dc → 17 mesh / 94 dc（省 144 dc，约 8%）**。

**不实施理由**：`probe_boat_p7v3.gd` 有 38 条 + `probe_verify_p7v3.gd` 有 15 条断言是
**按节点名逐件验证船体结构**的（`GunwaleS%02d`/`InnerFloor`/`Thwart00`/`OarShaftP` 等）。
合批会推翻这 53 条断言，需要把它们整体改写成"读溯源清单"的形式。
在性能门槛已达成（见 §6）的前提下，为 8% 的 dc 收益削弱对小船结构的验证力度不划算，
故**保留小船不合批**，把这条路径记录为可选方案（§10）。

### 4.5 未使用的备选手段及原因

- **MultiMeshInstance3D**：适合"完全相同的重复件"。实测本工程里楼梯踏步的尺寸逐级不同
  （Flight A 14 级 `1.10×0.06×0.295`、Flight B 11 级 `0.295×0.06×1.17` 按索引递增位置），
  栏杆立柱高度随踏步变化 —— 强行用同一网格会改变几何。同材质合批已达成同等收益，未采用。
- **合并成单一巨型网格 / 跨区域 MultiMesh**：明确禁止，且会破坏视锥剔除粒度，未采用。

## 5. toon 描边通道分析与视觉代价评估

### 5.1 描边管线的实际结构

- `isle_math.toon_material(color, {outline: w})` 在 `w > 0` 时设 `next_pass = outline_material(w)`；
- `outline_material` 按宽度缓存（`_outline_cache`），`toon_material` 按
  `颜色|bands|soft|rim|wind|glow|vc|outline_w|self_lit` 缓存（`_mat_cache`）——
  **不存在重复的描边材质实例或重复 pass**；
- `outline.gdshader` 极简：`VERTEX += NORMAL * outline_width`（模型空间）+ `unshaded + cull_front`，
  fragment 只输出常量色 + 远处抖动剔除。

### 5.2 描边通道的成本量化（实验，不提交）

在独立 worktree 里把 `toon_material` 的 `outline_w` 强制为 0（仅作测量），跑同一 `--perf`：

| 机位 | V3.1（有描边） | 关闭描边（实验） | 差值 |
|---|---:|---:|---:|
| noon_clear fps | 153.2 | 165.7 | +8.2% |
| noon_clear draw_calls | 1804 | 991 | **-813（占 45%）** |
| quality_2 draw_calls | 1573 | 870 | -703 |

**结论**：描边通道确实占了当前 draw call 的 45%，是 P7-V3 把新增部件成本放大的机制
（每个新部件 ×2 pass）。但**合批已经把这份增量几乎完全吸收**：
V3.1 的描边成本 ≈813 dc，P7-V2 估算 ≈790 dc —— 相对 V2 只剩约 **+23 dc**。
因此**没有做出任何描边妥协**：未关闭全局描边，未对任何一类物体单独关描边，
未改 `outline.gdshader`。任务书要求的"有实证支持才改"本次没有任何一侧站得住脚。

### 5.3 视觉等价性验证（三层证据）

**(a) 同机位 39 张验收图 + 同版本噪声基线 + 纯合批对照**

`probe_frame_p7v3.gd --stage=all` 拍摄 39 张，做三组对比：

| 对比 | 静态机位可见差异（>16/255 像素占比） |
|---|---|
| P7-V3.1 第 1 次 vs 第 2 次（同版本噪声基线） | 0.000% ~ 0.435% |
| P7-V3 vs P7-V3.1（跨版本） | 楼梯/室内/二层/门正背关/灯笼/门廊夜：**0.000% ~ 0.094%**（与噪声同级） |
| 同代码仅关合批 vs P7-V3.1（纯合批影响） | 同上量级 |

高差异图（boat_*、cat_*、door_open/anim、porch_wide_*）经**差分图目检**确认差异全部落在
动态内容上：

- `porch_wide_dusk`：**房屋本体差分全黑（像素级一致）**，差异全在风吹草地与云；
- `attic_window_inside_day`：**室内（窗框/台灯/桌面）差分全黑**，差异全在窗外海面波浪；
- `cat_back_day`：差异是尾巴摆动/耳朵抽动相位，猫本身未被合批；
- `door_open_day`：差异是开门动画捕获时刻不同（门扇角度不同），其余全黑。

**(b) 官方 `--shots` 74 张（61 场景 + 13 过渡帧）**

⚠ 该入口含大量动态内容（鸟/草/云/海/猫/船/转场动画），**其运行间噪声本身不可控**：
同版本重跑之间 `02_noon_sky.png`（纯天空，无任何合批对象）也存在 0.028% 可见差异，
跨版本为 0.447%。因此**官方截图不作为视觉等价的定量证据**，只做目检抽查。

目检结论：`01_noon` / `03_stairs_close` / `03_interior` 等关键图上，**房屋区域差分全黑**，
差异集中在鸟的位置与草地/花朵的风摆动。

**(c) 自动化断言支撑**

`probe_verify_p7v3.gd` 178 条断言全过（175 条原断言一条未删，见 §8.2），
其中包含拱券尺寸/形状、门扇零件数、踏步级数与顶面高度、井壁面数、一层天花板分块、
二层栏杆与立柱高度、吊灯位置、壁炉石体尺寸等**逐部件几何断言** —— 这比像素差更能证明
"几何没有被合批破坏"。

### 8.4 长时间运行（soak）

条件：`--minutes=12`，实际墙钟 **769 秒（12 分 49 秒）**，72 个采样点（每 10 秒）。
期间每 60 秒做一轮真实交互，四轮循环轮转：

1. 进入自由视角 → 2s → 退出；
2. 打开菜单 → 2s → `close()` → `_enter_playing()`；
3. 画质 `3 → 1 → 2` 切换；
4. FOV 65→42、自动运镜开/关、时间推进 1 小时。

| 指标 | 起始 | 结束 | 判定 |
|---|---:|---:|---|
| nodes | 1491 | **1469** | 稳定（t=20s 后恒定 1469，交互期间临时到 1483 并回收） |
| orphan nodes | 0 | 22 | 启动期一次性，之后不变 |
| resource_count | 45 | **45** | **零增长** |
| VRAM (MB) | 598.9 | 599.1 | +0.2 |
| objects（本帧） | 1874 | 2213 | 随相机/时段波动，无趋势 |
| draw_calls（本帧） | 1784 | 1815 | 同上 |
| FPS 中位数（全程 / 末 6 次） | — | 79 / **79** | **无恶化** |
| 猫咪待机时钟 | 10.33s | **766.34s** | 持续推进，未卡死 |
| ObjectDB / RID 告警 | — | 无 | stderr 无泄漏报告 |

**需要如实记录的异常**：`memory_static` 176.0 → 190.2 MB（+14.2）。趋势并非线性：

- t=10~110s 稳定在 176.0~176.4；
- **t=120s 一次阶跃到 189.1（+12.7MB）** —— 正好是 cycle 2「画质 3→1→2 切换」之后；
- 之后 t=120~720s（10 分钟）仅 +1.1 MB，且 `resource_count` 始终 45。

解读与局限：该阶跃与"切入高画质档（msaa 3 / scale 1.2~1.5）时分配中间渲染目标"同步，
属于引擎/驱动分配器行为；但由于没有做"纯待机不切画质"的对照，**不能排除**它是未回收分配。
**结论只写：本次 soak 未发现明显异常，不能据此宣称不存在内存泄漏。**

**若没有做启动验证，这个坏包会被直接交付。**

## 12. 必答问题

**Q1：P7-V3.1 的性能门槛是否真正通过？**
是。14 个基准机位（9 CPU-bound + 2 GPU-bound + 3 其余画质档）的中位数**全部**在 P7-V2 的
90% 以上；最差 quality_0 为 -9.5%（且该档 draw_calls/objects/VRAM 均优于 V2，波动跨度 14%，
详见 §6.3 的原始数据）。判定依据是本轮现场实测的 5 轮中位数，不是旧报告数字。

**Q2：主要 CPU-bound 场景是否恢复到 P7-V2 基线的 ±10% 范围？**
是，而且远超要求：9 个 CPU-bound 机位为 -3.6% ~ +2.6%（noon_clear 159.6→153.8，-3.6%）。
其中 `lite_night_nomultimesh`（+2.6%）与 `quality_2`（+1.0%）**反超** P7-V2。

**Q3：P7-V3 的视觉收益是否得到保留？**
是。三角形 191656 / 顶点 167727 与合批前**逐位相等**；`unique_materials` 仍为 274
（材质对象原样复用，未复制、未替换）；描边通道零改动；39 张同机位截图中静态机位可见差异
≤0.094%（与同版本重跑噪声同级），高差异图的差分经目检确认全部落在鸟/草/海面/猫尾/门扇动画相位上，
**房屋与室内差分全黑**。

**Q4：是否还有必须处理的稳定性或体验问题？**
没有发现必须处理的阻塞问题。有两条**建议后续跟进但本轮不阻塞**：
1. soak 中 `memory_static` 有一次 +12.7MB 阶跃，与"切入高画质档"同步，之后 10 分钟仅 +1.1MB。
   本轮未做"纯待机不切画质"对照，因此无法判定性质 —— 建议下次做长时段对照实验。
2. quality_0 是性能余量最小的档位（-9.5%），建议下次测量重点关注。

**Q5：当前分支、HEAD 和发布版本分别是什么？**

**Q6：哪些项目尚未验证？**
见 §9.3 八项，其中最重要的是：**真人键鼠手感未验证**、**音频未做听觉验证**、
