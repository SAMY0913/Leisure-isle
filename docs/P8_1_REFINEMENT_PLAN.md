**数据处理原则（写入第 7 章）**：

1. 同一小时只归入一个互斥基础天气类别（晴/多云/阴/雨/雪/雷暴/台风影响），风、云量、降水强度作为独立连续变量保留，避免同一小时重复计数。
2. 雨日按小时+过程统计，而不是按天计数，以区分小雨/中雨/大雨。
3. 台风按事件统计（路径进入影响圈），并列出三年样本实际次数；超出样本频率的部分用更长时期官方气候资料交叉检查。
4. 三年无自然降雪记录时不得编造降雪次数；保留手动选雪，自动降雪权重按「人工/艺术化可选项」给出并标注依据不足。
5. 所有脚本、参数、原始数据路径、输出表都记录在 开发产物/p81/weather/，任何人可按命令复跑。

### 5.2 浮空根因（已证）

1. 冬季 `canopy_keep=0.10`（isle_season.gd:55），44 个球中保留 `round(44×0.10)=4` 个（main.gd:983）。
2. 隐藏机制 `_apply_season_keep`（main.gd:1036-1050）：对每个 MultiMesh 缓存实例变换并按确定性洗牌（main.gd:918-925，rng seed 由节点名+kind 哈希决定）得到顺序，保留顺序前 90%、把尾部实例 basis 缩到 1e-4。**保留球停留在其原始随机位置，不移动、不重新锚定。**
3. 决定性证据：44 个球里 layer2/3 共 25 个球心局部 y≥9.45，**高于树干顶 9.30 与全部枝端 ≤7.93**；随机保留 4 个时，至少一个落在 layer2/3 的概率 = 1 − C(25,4)/C(44,4) ≈ **90.7%**。即使落在 layer0（y≈7.4±0.55），球心环半径 0–4 m，与枝干仍无几何连接。
4. 保留球呈黄绿色而非枯色：冬季 `foliage_tint=(0.88,0.78,0.66)`（isle_season.gd:53）在 toon.gdshader:206 乘到黄绿顶点色上，只能压暗偏色，不能去饱和变枯。
5. **结论**：不能靠降低树冠保留比例或截断实例数量解决；必须做到「冬季可见的树冠与真实枝干几何相关」。推荐直接 `canopy_keep=0.0`（零残留 + 真裸枝），而不是给树冠球加枝干锚定（后者工作量大、球冠形态也与裸枝语义冲突）。

## 6. 冬季全岛渐变白化与室内豁免（任务书 §3 对应）

> 本章基于 Lead 独立读码与 snow_light.md（599 行，含 file:line、方案对比、性能估算、18 条未验证清单）核对。性能数字均为估算，标注为未实测。

### 6.0 现状反证：三个必须先解决的缺陷

1. **白化根本不存在**：全仓 grep `whiteness|winter_white` 0 命中；唯一与雾/雪相关的全局量是 `g_weather`(rain,snow,wetness,snow_cover)、`g_weather2`(cloud,storm,wind,indoor)、`g_wind_dir`、`g_lightning`。冬季只能靠「恰好在下雪」临时变白；2026-01-15 晴天（P8 截图 p8_season_winter_wide.png 已证）整岛仍是绿草绿树。
2. **室内雪是代码路径必然结果**：toon.gdshader:262-276 的积雪项为 `snow_m = up_mask * noise * snow_line(world.y 1.05-3.20) * snow_cov`，**没有任何室内/室外判定**。室内地板、床、桌、柜台均为 toon 材质、朝上、世界高度约 9 m；虽然 snow_line 在 3.2 处已衰减为 0（世界高度与地形高度约 7.4-7.9 的对应关系本身需实测复核，见 6.7 #1），但一旦后续把雪线改成相对地形高度，室内朝上表面会立即积雪。本轮设计必须在加入「全岛白化」的同时把室内豁免做进去。
3. **现有 indoor 全局量是「摄像机判定」且无人消费**：main.gd:1184-1185 计算 `g_weather2.w = 平滑后的相机在小屋壳内标志`，但全部 shader 无一处读取。任务书明确禁止用相机判定解决室内豁免，因为它无法处理「站在屋外透过窗户看室内」——相机在屋外时整屋按室外处理，室内被刷白。**本方案不消费、不扩展、不复用该量。**

### 6.1 两个概念必须分离（winter_whiteness 与 snow_cover）

| 概念 | 驱动来源 | 游戏含义 | 现有代码 |
|------|----------|----------|----------|
| `winter_whiteness` | **季节**（isle_season 冬季权重 + 日期） | 深冬整岛逐渐失去饱和度、地表泛白/霜白，即使晴天也白 | **不存在**，需新增 |
| `snow_cover` | **天气**（isle_weather 的 `snow_depth`，积累约 9000 s / 消融约 14000 s） | 真实降雪后的地面积雪厚度 | 已有，作为 `g_weather.w` 传给 shader |
| `wetness` | 天气（rain/snow 后 ~420 s 湿/5400 s 干） | 雨雪打湿表面变暗 | 已有，`g_weather.z` |
| `frost_amount` | 季节 × 温度（夜间/晴冷） | 朝上表面的白霜，不覆盖、不遮挡纹理 | **不存在**，可由 whiteness 派生 |

**为什么不能合并**：① 晴天、无降雪的深冬地面也应泛白（现实中的枯草+霜+低饱和）；② 台风残余/异常年份的晚秋或早春若手动降雪，snow_cover 可以非零而 winter_whiteness 为 0；③ 两个参数的时间尺度差两个数量级（季节 90 天 vs 积雪数小时），合并后无法同时满足「渐变」与「积雪消融」。

**参数定义（建议，P8.1-03 实现）**：
- `winter_whiteness = smoothstep(0.30, 0.90, winter_weight)`，与季节权重同步、单调、无跳变；冬季权重已在 isle_calendar.gd 内由 ±10 天 smoothstep 生成（B 级：按现有公式复算，2026-12-01=0.514、12-06=0.830、01 月=1.0、02-26=0.553）。
- `frost_amount = winter_whiteness * 0.65`（艺术常量，可被各材质接收系数缩放；温度模型不存在，不引入）。
- `ground_tint = winter_whiteness`；`foliage_desat = winter_whiteness`。
- `snow_cover` 继续由 isle_weather 的 snow_depth 归一化供给（现有 uniform 不改名，仅扩展消费方式）。

### 6.2 数据通路与 Shader 改动点（不新增 draw call 的路径）

| 位置 | 现状 | 改动 |
|------|------|------|
| `RenderingServer.global_shader_parameter_*` 设置 | main.gd 每帧设 `g_weather`/`g_weather2`/`g_wind_dir`/`g_lightning` | 新增 `g_winter`(whiteness,frost,ground_tint,foliage_desat)、`g_house`(origin xyz + yaw 打包)、`g_house2`(half_x, half_z, floor_min, floor_max)、`g_roof`(ridge_y, tan_pitch, eave_y, roof_half_z)；房屋/地形静态，可只设一次，白化量每帧只更新 `g_winter` |
| toon.gdshader | 顶部 uniform 列表；:206 foliage tint；:262-276 snow block | 声明新 uniform；新增 `indoor_mask()` 函数；在 wet 之后、snow 之前插入 frost/desat/ground_tint；snow 项乘 `(1.0-indoor) * snow_recv`；对 self_lit 提前返回的材质保持零雪接收 |
| grass.gdshader | :80 混 55% 白，无 indoor | 新增 `snow_recv`/`frost_recv`（默认 1.0）；雪/霜项乘 `(1.0-indoor_mask(world_pos))`；加 up_mask（现在垂直草叶也刷白 55%） |

关键：白化不是「新增第二套材质」，而是**同一批 toon 材质加少量逐片元计算**。对象数量不变、draw call 不变、节点不变；这是能守住 P8 性能预算的唯一路径。

### 6.3 室内判定：逐片元体积掩码（相机无关）

核心函数（GLSL 伪代码，实际以房屋真实坐标/朝向常量赋值）：

```glsl
// 返回 1.0=室内（豁免），0.0=室外
float indoor_mask(vec3 wp) {
    vec3 lp = mat3(g_house.w_cos, 0.0, -g_house.w_sin,
                   0.0, 1.0, 0.0,
                   g_house.w_sin, 0.0, g_house.w_cos) * (wp - g_house.xyz);
    if (abs(lp.x) > g_house2.x || abs(lp.z) > g_house2.y) return 0.0;   // 平面范围外
    float roof = g_roof.x - g_roof.y * abs(lp.x);                        // 坡屋面底
    if (lp.y < g_house2.z - g_house2.w) return 0.0;                      // 一层地面以下
    if (lp.y > roof) return 0.0;                                         // 屋面以上（外墙顶/屋顶外表面）
    return 1.0;
}
```

**几何常量（B 级，来自 snow_light.md §2 与 cottage.gd 复核）**：房屋原点与朝向从 cottage 节点读取（世界位置与 yaw；本方案把它作为常量推给 shader，房屋不可移动），一层内空约 x∈[-3.50,3.50]、z∈[-2.80,2.80]、y∈[0.57,2.97]（相对地板）；阁楼地板 y≈3.19，屋面底 `roof = ridge_y - tan(pitch)*|x|`，ridge_y≈6.20，tan(pitch)≈0.650（坡角约 33°，与截图屋面倾角一致）。**这些数值在 P8.1-03 必须用 Godot 运行时实测复核（尤其屋脊方向：现假定沿 z 轴、坡面朝 ±x）**，复核后写入计划常数。

**为什么该判定天然满足任务书要求**：
1. 与相机无关：只看片元世界坐标，屋外透过窗户看室内时室内片元仍返回 1.0，不会白化。
2. 进入一楼/阁楼/站在门廊：室内表面始终 1.0，室外表面始终 0.0，表现一致。
3. 外墙/屋面**同一材质、内外两面**也能区分：外墙外表面在 |x|>half_x 或 y>roof，外表面朝外 → 0.0；内表面在体积内 → 1.0。不依赖材质名，不依赖「室内专用材质」。
4. 窗户玻璃：玻璃片在墙体内（|x|≈3.5）恰处边界，**不能靠体积赌边界**；玻璃材质显式设 `snow_recv=0.0, frost_recv=0.15, ground_recv=0.0`，只做轻霜，不做积雪。

**为什么不用材质身份做唯一依据**：室内地板/墙与室外同类材质可能同源；同一 toon 材质被多个物体共享（缓存复用），逐物体加参数会破坏材质合批。故 S1（体积掩码）是主方案，S2（对象/材质身份）只作补充。

### 6.4 豁免分级（S0-S4）与推荐组合

| 方案 | 做法 | 成本 | 优点 | 缺陷 |
|------|------|------|------|------|
| S0 | 不做室内豁免 | 0 | 无 | 室内刷白/积雪（任务书禁止） |
| S1 | 逐片元体积掩码（本节 6.3） | 每片元约 10-20 ALU，零 draw call | 相机无关、内外统一、覆盖全部室内几何 | 边界处（窗框、门套）可能出现 1-2 px 过渡 |
| S2 | 室内专用材质/对象白名单 | 零运行时 | 精确 | 共享材质与合批冲突、维护脆弱、外墙内面无法区分 |
| S3 | 室内衬里几何（interior liner） | draw call +1~3 | 彻底解决边界过渡 | 新增几何/内存，且需与门窗开口对齐 |
| S4 | 材质分类接收系数（snow_recv 等） | 零运行时 | 表达玻璃/金属/雪面差异 | 不处理内外 |

**推荐组合：S1（必做） + S4（必做） + S2 仅用于阁楼玻璃/发光体等例外 + S3 只在截图发现边界缺陷时启用**。三者均与相机无关；任务书「室内豁免必须根据物体实际类别或材质身份实现」在本方案中由「体积掩码（位置身份）+ 材质接收系数（类别身份）」共同满足，**不消费相机 indoor 标志**。

### 6.5 室外覆盖清单与材质分类（不允许无差别刷白）

| 对象 | 现状材质 | 白化/积雪接收 | 理由 |
|------|----------|---------------|------|
| 地面、草地 | terrain 顶点色 + GrassMultiMesh | ground_tint 1.0、snow 0.9、frost 0.6 | 地面是白化主承载；草叶按 up_mask 减半 |
| 道路、砂石、草丛 | toon 顶点色 | 同地面 0.9 | 与地面连续 |
| 岩石 | toon 顶点色 | snow 0.9、frost 0.4、ground_tint 0.5 | 石头本身灰，白化弱化；积雪强 |
| 房屋外墙 | toon 顶点色 | snow 0.85、frost 0.35、ground_tint 0.6 | 木/灰泥墙；垂直面自然少积雪 |
| 屋顶瓦片 | toon 顶点色 | snow 1.0、ground_tint 0.4 | 坡屋面持雪 |
| 屋檐、门廊木构 | toon | snow 0.8 | 木构件持雪少 |
| 灯塔本体/平台/石阶 | toon | snow 0.9、ground_tint 0.6 | 石+混凝土 |
| 码头、木栈道、室外家具 | toon | snow 0.8、wet 1.0 | 木材吸收湿暗 |
| 树干、裸枝 | toon（棕） | snow 0.5（向上面）、ground_tint 0.3 | 枝上只有薄雪 |
| 常绿灌木/背景树冠 | toon 顶点色 | foliage_desat 1.0、snow 0.55 | 冬季降饱和，不许全白 |
| 玻璃（窗/灯塔） | glass 自定义 | snow 0、frost 0.15、ground_tint 0 | 玻璃不积雪，轻霜 |
| 金属（灯具支架/栏杆） | toon | snow 0.25、frost 0.3 | 金属挂雪少 |
| 发光材质（灯罩/火焰/窗内暖光） | self_lit | snow 0、frost 0、ground_tint 0 | 不允许刷白 |
| 海面/天空 | sea/sky shader | 不参与 | 见 6.7 #8 |

**实现顺序（每个 toon 片元）**：湿暗（已有）→ frost 混白（按 up_mask 与 frost_recv）→ foliage 去饱和（只对叶类）→ ground_tint 混色（只对地面类）→ 积雪项最后叠加（`snow_recv * snow_cov * up_mask * noise * (1-indoor)`）。所有冬季项统一乘 `(1.0 - indoor_mask(wp))`，一次求值、多处复用。

### 6.6 性能与五档画质

- 额外 uniform：4 个 vec4（`g_winter`、`g_house`、`g_house2`、`g_roof`），每帧最多 1 个更新（`g_winter`），其余启动时设一次；不新增纹理、不新增材质、不新增节点。
- 逐片元成本：mask 约 10-20 ALU + 3 次 mix，估算 q2 增量 <0.3 ms（未实测，按 P8 每 draw 片元数与学生机 RTX2060 估算）；skinning 材质同样适用。
- 五档画质：**白化效果本身五档一致**（这是视觉承诺，不是特效）；可降级的只有积雪噪声细节（q0 用 2 八度、q4 用 4 八度）与草叶数量（已有）。不允许 q0 直接关闭白化。
- 预算守卫：draw call +0（不加 liner 的前提下）、节点 +0、VRAM +0；帧时间预算 +0.3 ms，P8 已实测的 clear 5.56 ms 下仍留有大量余量。若 S3 liner 启用则 draw call +1~3、节点 +1~3，需单独记账。

关键交叉校准结论（crosscheck_summary.csv）：

1. **风速**：重叠 3087 小时，ERA5 均值 4.91 m/s，ISD 均值 3.53 m/s，偏差 +1.38 m/s，MAE 1.93、RMSE 2.47、相关 0.703。逐日月均相关 0.826、日最大相关 0.839。为把 ERA5 10 m 海面网格风折算到站点尺度，采用 `station_wind_factor=0.78`（ISD 月均比中位 0.727，取 0.78 后 >=10.8 m/s 的强风小时 19h，ISD 实测 21h，量级一致）。
2. **降水**：ERA5 对毛毛雨明显高估。0.1 mm/h 口径下 ERA5 有 892 小时、ISD 367 小时（precision 0.32、recall 0.78）；0.2 mm/h 口径下 675 vs 367（precision 0.37、recall 0.69），是更接近的折中。因此**分类主口径取 0.2 mm/h**，0.1 mm/h 的敏感度数字记录在本节，不单独出表（原计划的 table_precip_threshold_sensitivity.csv 未生成，见 7.10）。
3. **雷暴**：ISD 同期雷暴日 13 天，CAPE 代理 14 天，命中 4 天（precision 0.29、recall 0.31）。代理只能给“约每季多少天”的量级，不能逐日复现；报告中所有雷暴比例均标为代理估计。
4. **温度/降雪**：三年 Tmin=11.6 ℃（2022/23 冬），全期 <10 ℃ 小时数为 0，<12 ℃ 仅 17 小时；ERA5 snowfall 0 小时，ISD 无雪标记。**澎湖三年自然降雪为 0 是可靠结论**，不是缺测推断。

### 7.2 互斥分类规则（每小时唯一基础类别，优先级从高到低）

- 阈值全部集中在 compute_stats.py 顶部常量；改动阈值后重跑即可复现。注意 compute_stats.py 文件头注释仍写“大雨 >=7.5、中雨 2.5—7.5”，而实际常量是 `RAIN_MID_MAX=8.0`（JSON meta 亦为 8.0），**注释与实现不一致**；本章以常量 8.0 为准，并把该不一致列入第 13 章 U 清单。

1. **heavy_rain 的“过程频率下限”**：观测小时占比下 heavy 仅 3 小时全年（0.011%），若直接映射，游戏里约 10 年才出现一次，体验上等同于不存在。但大雨是游戏内强视觉事件（重雨幕、雷电联手、生态联动），且观测的 heavy 小时被 ERA5 平滑严重低估（再分析对对流性短时强降水峰值有明显削峰，ISD 2025 年 6—8 月已记录多次 >8 mm/h 而 ERA5 对应小时常 <2 mm/h）。因此 heavy_rain 采用**过程频率下限**：按降水过程峰值分级，heavy 过程频率为夏 1.667 次/年、秋 1.0 次/年，除以该季每年天气轮数（夏 794.9 轮、秋 786.2 轮）再乘 100，得夏 0.21、秋 0.13，差额从 light_rain 中扣除（春 11.29、夏 18.37、秋 8.23 已是扣除后的值），使“一轮天气 ≈ 一次降水过程”。该调整只改变**视觉事件可见性**，不改变“降水总时长占比”。
2. **winter 雪**：`table3_game_mapping.csv` 的 winter 行保留艺术化权重 0.4/0.15/0.05（小雪/中雪/大雪，合计 0.6，从 clear 中扣除 0.60，不引入第 101 个百分点）作为**手动/艺术化选项**，对应约每季 3—4 个游戏日的降雪；但 `sim_meta.json` 的 `new_weights`（自动模式实施口径）中雪全为 0。两者不矛盾：**自动权重必须为 0（三年无雪）**；若产品希望冬季自动模式偶尔下雪，需单独开关并把 0.4/0.15/0.05 作为“艺术化可选档”，写入设置项而不是偷偷混进自动权重。实施时注意 `tools/probe_p8_weather.gd:357-365` 现有断言假定冬季可自动出雪，需同步改为“自动模式无雪 + 手动可注入”。

### 7.10 未验证与数据薄弱项（详表见第 13 章）

1. 雷暴为 CAPE 代理，ISD 校准 precision/recall 仅 0.29/0.31，季节形态可信、绝对比例不稳。
2. ERA5 对对流性强降水存在削峰，heavy_rain 的真实频率可能高于 0.011%，当前用“过程频率下限”补足，属**工程折中而非观测值**。
3. ISD 只有 2025-02—08，不能覆盖秋冬强风季，秋冬强风比例完全依赖 ERA5 与 station_factor=0.78；若拿不到澎湖站 2023—2024 完整逐时数据，该系数无法在秋冬二次验证。
4. 300 km 台风影响圈是工程阈值（澎湖常见“海上警报”半径），未逐事件核对 CWA 警报发布记录；11 个事件的数量级可信，但“影响小时”对距离/强度敏感。
5. compute_stats.py 的阈值注释与实现不一致：docstring 第 28—30 行仍写旧阈值 7.5/0.1，常量第 61—63 行为 0.2/2.5/8.0，out/ 全部结果按后者生成；实施阶段改注释即可，不重算数据。
6. 冬季权重使用了含残季的 6504 小时合并值（2022/23 冬缺 12 月、2025/26 冬只有 12 月），与完整冬季相比可能有 ±2 个百分点偏差。

### 8.2 落叶：从“斜飞”改为“风场输运”

**目标行为**：无风/轻风时叶子缓慢飘落、几乎垂直；风越强，落速越快、横向位移越远、姿态越倾斜、旋转越剧烈，且全部向下风向移动；离开树干后按物理下落，消失时不瞬移不硬切。

**粒子参数（fx.gd `_leaf_fall` 内，保持现有 GPUParticles3D + ProcessMaterial，不新建每叶节点）**：

| 参数 | 现值 | 新值/公式 |
|------|------|-----------|
| amount | 96 | 保持（质量档缩放沿用 main.gd:5078-5107，q0 约 60/q4 约 144） |
| lifetime | 9.0 | 9.0（不改，靠下落时间约束自然收尾） |
| preprocess | 6.0 | 6.0 |
| emitting | false（手动 burst） | false |
| position | 大树顶部 y13.6（main.gd:602） | 保持 |
| aabb | 28x18x28 | 36x20x36（强风横向漂移变长，避免出视锥被剔除） |
| direction | (0.12,1,0.06) | `normalize(wd.x*wv*(1.6+1.8*tr), 1, wd.y*wv*(1.6+1.8*tr))` |
| spread | 70 | 50（强风方向更集中，才会“成片顺风走”） |
| v0 初速 | 0.05—0.32 | 0.05—0.32（不改） |
| gravity | (0.10,-0.55,0.05) | `(wd.x*wv*(0.55+2*tr), -(0.55+0.10*wv+1.35*tr), wd.y*wv*(0.55+2*tr))` |

其中 `wv=wind_strength`（main.gd:1220-1227 每帧已算）、`tr=smoothstep(0.40,0.95,wv)` 为“强风输运因子”、`wd=(sin(wind_yaw), cos(wind_yaw))` 为现有风向单位向量（main.gd 已有）。

**数值验证（wind_ui.md 已算）**：叶片从 y≈13.6 落到地面 y≈7.4，落差 6.2 m。

| 天气 | wv | tr | 下落时间 | 横向漂移 | 倾角 | 评价 |
|------|----|----|---------|---------|------|------|
| clear | 0.18 | 0.00 | 4.83 s | 1.43 m | ~12° | 轻风自然 |
| light_rain | 0.36 | 0.00 | 4.83 s | 1.43 m | ~12° | 与 clear 一致（合理：叶子由季节掉，不因下雨改变） |
| strong_wind | 0.88 | 0.96 | 2.47 s | 7.08 m | ~71° | 落速 +95%，横向 4.9 倍，肉眼可辨 |
| typhoon | 1.0 | 1.00 | 2.44 s | 7.3 m | ~74° | 略强于强风，平滑连续 |

**季节门控（必须修，否则冬季掉绿叶）**：`_update_leaf_fall` 当前直接使用 9 个权重（秋 1.0→0.15→冬），过渡期冬季权重 0.15 时仍可能掉绿叶。改为：`leaf_gate = clamp(1 - winter_w*1.35, 0, 1)`（winter_w>=0.74 即 12 月中旬后完全关闭），并在 `emitting` 判断里用 `leaf_gate>0.02`；同时把颜色向秋季橙偏一点避免“冬季掉嫩绿”：`color = color.lerp(Color(0.95,0.52,0.18,1), clamp(winter_w,0,1)*0.35)`。春季权重回升时 leaf_gate 平滑放开，不存在“跳到冬季就全关”的突变。

**生命周期**：重力改为随 tr 增加下坠速度后，落地时间从 4.4s 缩到 2.4—2.5s，远小于 lifetime 9s，因此仍需处理“落地后地下停留”。方案：让 `color_ramp` 的 alpha 在 offset 0.55（强风下落结束附近）已经开始衰减到 0（即 alpha 曲线 [0, .95, .30, 0]，offset [0,.12,.55,1]），并在 `LeafParticles` 的 `process_material` 中开启 `collision` 无必要（成本高）。**更简单**：把 `lifetime` 从 9 降到 5.0、`preprocess` 从 6 降到 3，因为叶子 2.5—4.8s 必然落地；这会让 GPUParticles3D 的粒子存活时间与视觉一致，且减少“地下残留粒子”的无效更新。同时保留 `emitting=false` 的 burst 机制，不重建粒子系统。

**验收（F 编号）**：

- F1 f(x)=clear 无风时，落叶垂直下落、落地前淡出，无地下残留（截图 3 帧差）。
- F2 strong_wind 时，落叶落速与横向位移显著大于 clear（用 probe 读 ProcessMaterial 的 gravity/angular_velocity/direction，断言 tr 公式值）。
- F3 风向改变（wind_yaw 旋转 90°）后，新发射落叶立即改变方向，已有叶子不瞬移（混用旧粒子属物理合理，不要求一致）。
- F4 冬季（winter_w>=0.80）时，落叶 `emitting=false` 且连续 30 s 无新叶子；春回后 5 s 内恢复。
- F5 秋千/落叶都不因 draw call 或节点数增加（仍在同一 GPUParticles3D 内）。

### 8.3 萤火虫：三通道解耦 + 真正减算

**新公式（main.gd:1715-1728 替换）**：

`windf = 1 - smoothstep(0.55, 1.0, wind)`；`stormf = 1 - smoothstep(0.20, 0.70, storm)`；`precf = 1 - clamp(rain*1.9 + snow*1.9, 0, 1)`；`ratio = ffi * windf * stormf * precf`（ffi 为现有夜间基础可见性 0/1）。

`emitting = ratio > 0.02`；`amount_ratio = ratio`；`speed_scale = 0.45 + 0.55*ratio`；`emission_box_extents = (12,2.4,12) * (0.25+0.75*ratio)`；`albedo = (2.2,1.9,0.75) * (0.55+0.45*ratio)`。

**对比（旧 vs 新，clear=1.0 为基准）**：

| 天气 | 旧 ratio | 新 ratio | 说明 |
|------|----------|----------|------|
| clear | 1.00 | 1.00 | 不变 |
| strong_wind | 0.47 | 0.18 | 强风只剩 1/5，肉眼可辨 |
| light_rain | 0.46 | 0.43 | 接近 |
| mid_rain | 0.00 | 0.00 | 与旧一致（降水本就应清零） |
| thunder | 0.00 | 0.00 | storm 通道再次保证 0 |
| 强风+小雨叠加 | 0.00（旧公式降水项直接 0，风项被掩盖） | 0.08（三通道相乘，风/雨都可见） | 这正是“叠加冲突”要修的点 |

**“不能把 amount_ratio 当减算”**：Godot 4 的 GPUParticles3D 中 `amount_ratio` 只影响发射量，已发射粒子仍全程参与模拟与渲染。真正降低计算量的手段：`emitting=false`（停止发射，active 粒子在 lifetime 9s 内自然死完）、`speed_scale` 不改变粒子数、`emission_box_extents` 也不改变粒子数。因此本方案在 ratio 很低时让 `emitting` 直接关闭，并让 `lifetime` 在 ratio<0.25 时缩短到 4s（`lifetime = 4 + 5*clamp(ratio*2,0,1)`），使低谷期真正少算；**最终以 GPU 帧时间实测确认**（不能在文档里断言）。

**验收（F 编号续）**：

- F6 strong_wind 夜晚萤火虫可见数约为 clear 的 1/5（截图或粒子数读回）。
- F7 强风+小雨叠加时仍能看到少量萤火虫，不出现“完全黑掉”。
- F8 ratio<0.25 时 `emitting=false`，且 4—6 s 内粒子自然消失，无瞬移。
- F9 粒子系统不重启（`_firefly_node.restart()` 不得每帧调用）。
- F10 用 GPU 帧时间对比 clear vs strong_wind，确认低谷期有实际收益（否则记入第 13 章未验证）。

### 8.4 秋千：弹簧-阻尼受迫摆（不破坏 P7 冻结尺寸）

**几何现状（必须保持不动）**：BIG_TREE 基点 (-10.9, 7.8677, 4.2)；SWING_PIVOT_X=-7.90、Z=4.20、LIMB_Y=5.55 ⇒ 枢轴 (-7.90, 13.4177, 4.20)；绳长 5.2159 m；座椅 1.12x0.07x0.46、座面高 0.585 m（P7 合同 0.45—0.62）；枢轴无旋转 ⇒ **局部轴 = 世界轴**（x 轴前后摆、z 轴侧倾）。禁改：绳索长度、座椅尺寸、悬挂点、结构支撑。

**状态**：`_swing_roll` / `_roll_v`（绕 z 侧倾，正=向 +x 倾）、`_swing_pitch` / `_pitch_v`（绕 x 前后摆）。枢轴节点只改 `rotation = Basis.from_euler(pitch, 0, roll)`。

**受力（每帧）**：

- `tr = smoothstep(0.35, 0.95, wind_strength)`；`gust = 1 + (0.22*sin(t*1.13) + 0.13*sin(t*2.7+1.2)) * tr`（阵风包络，与风同向叠加）。
- `acc = (2.2*wind_strength + 0.8*tr) * gust`（m/s²，等效横向加速度）。
- `tgt_roll = atan2(wd.x * acc, 9.8)`，clamp 到 [-0.18, +0.42] rad；`tgt_pitch = -atan2(wd.y * acc, 9.8)`，clamp 到 ±0.45 rad。
- 弹簧-阻尼：`w0=1.3707`（对应周期 4.585 s，贴合现有 idle sin 1.15 rad/s 的观感）、`c=0.7676`（ζ≈0.56，有回摆但不上晃），用半隐式欧拉积分（`v += (w0²*(tgt-x) - 2*c*w0*v)*dt`，`x += v*dt`）。
- **无风时严格退回旧公式**（`rotation.x=sin(t*1.15)*0.42`、`rotation.z=sin(t*0.83+0.8)*0.06`）作为基础姿态，再把风致偏移叠加到旋转上，保证 `wind_strength=0` 的回归截图像素级一致。

**碰撞校验（用现有座椅/绳索几何算）**：绕 z 侧倾 -0.18 rad 时，座椅外缘距支撑柱仍有 0.458 m 余量；-0.20 时余量 0.357 m；-0.24 时余量 0.156 m（临界）；-0.28 已穿透。因此 roll 下限取 -0.18 安全；上限 +0.42 朝开阔方向，无碰撞。**不允许在 strong_wind 下让秋千撞柱或穿绳**。

**验收（S 编号）**：

- S1 无风回归：`wind_strength=0` 时前后 10 s 轨迹与旧实现逐帧误差 <1e-6（可用 probe 录制 rotation）。
- S2 strong_wind 下持续受迫摆动，roll 稳定在 ±0.18—0.42 区间的下风向一侧，且**下风向侧座面高度 > 平衡位置 > 上风向侧**（任务书要求“下风侧升高、上风侧降低”，注意不能写成“上风侧低于静止”，因为强风下整体会被抬起）。
- S3 风向 90° 改变后 3—5 s 内平滑过渡到新侧倾方向，无瞬移。
- S4 阵风包络导致周期内幅度有 10%—25% 起伏，但不出现恒速机械摆动。
- S5 绳索/座椅尺寸/悬挂点/支撑柱不变（P7 尺寸 probe 仍过）。
- S6 极端 typhoon 下 roll 仍被 clamp 在 -0.18，不穿模。

## 9. 壁炉、室内灯与码头灯的真实照明（任务书 §6 对应）

> 依据：开发产物/p81/findings/snow_light.md 第 1—12 条（599 行）。本章先给“引擎灯为什么无效”的实测式反证，再给 A/B 两方案对比与五档预算。

### 9.0 关键反证：加 OmniLight3D 不会照亮任何现有材质

以下为静态检索 + 代码路径结论（未运行引擎，但证据链闭合）：

1. `scripts/` 与 `scenes/` 全目录检索 `OmniLight3D`、`SpotLight3D`、`DirectionalLight3D` 节点：**0 个**。场景里没有任何引擎灯。
2. 所有材质 `render_mode` 为 `unshaded`（唯一例外是天空），`toon.gdshader`/`grass.gdshader` 内没有 `light()` 函数、没有 `LIGHT`/`ATTENUATION` 内置变量。**unshaded 材质不参与引擎光照管线**，即使运行时 `add_child(OmniLight3D)`，片元颜色也不变。
3. main.gd:535-536 显式关闭环境光与反射（`environment.ambient_light_source = DISABLED` 等价设置），场景没有 GI/反射探针。
4. 因此当前所有“灯光”都是**自定义解析光**：main.gd 每帧把最多 12 个灯塞进 `g_l0..g_l11`（vec4=xyz+range）与 `g_lc0..g_lc11`（rgb+energy），由 toon.gdshader:132-142 的 `add_point_light` 手工计算。

**结论（决定方案走向）**：要么把所有 toon 材质改成受光材质（方案 A，重写渲染路径），要么继续走解析光但补齐灯位与算法（方案 B）。任务书要求“先做最小光照原型确认自定义 Shader 收到哪些灯数据”——正是方案 B 的前提验证。

### 9.3 B 方案设计：16 槽 + 室内外双池 + 灯位补齐

**Shader 改动**：

- `g_l0..g_l15` / `g_lc0..g_l15`（16 槽，vec4）。grass.gdshader 同步从 8 槽扩到 16 槽（但不能像现在硬编码暖色 `vec3(1.0,0.78,0.48)`，改为读 `g_lc` 的 rgb）。
- 新增 `g_linfo = vec4(indoor0..3 flags, outdoor0..3 flags, ...)` 或直接用 4 个 `g_lflag`（每 4 槽一个 vec4），每槽 1 bit 表示该灯属于室内还是室外；片元端用体积掩码（第 6 章 `g_house` 那一套）决定“室内片元只吃室内灯、室外片元只吃室外灯”——**这就是零成本的室内外互斥遮挡**。
- `self_lit` 提前返回必须改：灯罩材质加 `light_mask` 或改为“先算自发光，再叠最多 1 个近距离灯”，让灯罩接受本体光（否则灯罩永远像贴纸）。
- 玻璃/海面/天空没有解析光通道：码头灯照海面必须**可选**新增 `sea.gdshader` 的 2—4 个反射光槽（只用于近岸码头灯，成本极低）；玻璃同理，至少让窗框内侧受光。

**排序策略（替代“能量优先”）**：分两个池，各自内部按“重要度 = energy * 场景权重 / 距离”排序：

- 室外池：6 盏路灯（强制）+ 灯塔 + 码头灯 + 门廊灯笼 x2 + 船上灯笼（动态，船可见时）+ 最近 1 盏窗灯。
- 室内池：壁炉 + 一层吊灯 + 阁楼吊灯 + 2 盏台灯 + 落地灯 + 阁楼暖光2。
- 每帧先按当前相机所在体积（第 6 章同款 `g_house` 掩码）判断“室内视角/室外视角”，再把**另一池**压缩到 1—2 槽保底（室外看窗内仍有微光，室内看窗外仍有码头灯），其余槽给本池——这样不会出现“在屋里时外面路灯占满 12 槽”或反之。

**五档预算（每档都必须有实际局部照明）**：

| 档 | 灯槽 | 必含 | 允许省略 |
|----|------|------|----------|
| q0 低·流畅 | 10—11 | 6 路灯 + 灯塔 + 一层吊灯 + 壁炉 + 最近台灯 | 门廊灯、窗灯、码头灯（改光池贴花）、船灯 |
| q1 中·均衡 | 11 | + 门廊灯笼 x1 | 窗灯、船灯、阁楼暖光 |
| q2 高·精致 | 12—13 | + 码头灯、阁楼吊灯 | 船灯、阁楼暖光2 |
| q3 极高·细腻 | 14 | + 全部室内灯 + 船上灯笼 + 门廊 x2 | — |
| q4 极致·电影 | 16 | 全开 + 海面反射 2 槽 + 窗灯 x2 | — |

低档“省略”的灯用**地面光池贴花**（一个带加色混合的 QuadMesh 贴图，每盏 <2 draw call）补足可见性，保证“夜晚门廊、码头仍有暖光落在地上”，而不是简单关灯。

**阴影近似（无 shadow map）**：

1. 室内外互斥就是最大的一层遮挡（墙/屋顶不投影也不会互相漏光，因为片元按体积掩码选池）。
2. 家具遮挡用“可复用 ray-AABB 遮挡”——main.gd 已有 `g_occ_*` 模式的框架（楼梯/树冠用过），为桌、沙发、床各注册 1 个 AABB，片元端对最近 3—4 个灯做一次 ray-box 测试，被挡则乘 0.15。
3. 家具底部的 blob 阴影（椭球贴花）补“接触感”。
4. q2+ 已有后处理 AO 保留，q0/q1 不用。

**壁炉专项**：energy 1.5—2.0、range 4—5（当前 1.20/4.0 偏弱）、**所有档位都激活**（q0 起即可，它是室内唯一“必须亮”的地方）、每盏独立闪烁（`1 + 0.12*sin(t*7.3) + 0.06*sin(t*13.7+2.1)`，与全局 `fl` 解耦）、地面加一个暖色光池贴花（半径 ~2.2 m）、火焰用 2—3 层滚动的噪声面片（不是新粒子系统），可选的 8—12 个火星粒子（仅 q2+）。

**室内灯昼夜调光**：现在室内灯罩 `self_lit` 恒定，白天也“亮着”。改为 `self_lit_strength = base * (0.25 + 0.75*night_factor)`（`night_factor` 用 main.gd 现成的太阳高度/环境亮度），同时解析光 energy 同步——白天灯罩微亮、夜晚全亮，符合真实观感。

**码头灯**：energy 1.60 range 10（q2+ 必含），除解析光外新增“海面倒影”2 个槽（仅 q4）或一条竖直方向的高光贴花（低档）；保证“灯柱周围木地板有光池、海面有暖色反光”。

### 10.2 组件结构

新文件 `scripts/ui_datetime_wheel.gd`：

```
class_name IsleDateTimeWheel extends Control
  signals: parts_changed(parts: Dictionary), editing_changed(busy: bool)
  var _cols: Array[WheelColumn]  # 5 个列子控件（自绘，不用第三方）
  func setup(font: Font, editable: bool) -> void

```

每个 `WheelColumn` 是 `Control` 子类，`_draw()` 绘制当前可见的 5 行（中心行 16px 高亮、相邻 13px alpha .62、再外 10px alpha .32），中心条用 `draw_rect`；`_gui_input` 处理滚轮（`MOUSE_BUTTON_WHEEL_UP/DOWN`）、按下/拖动/释放、点击行。**滚轮必须 `accept_event()`**，否则事件会冒泡到 main.gd:2031-2142 的相机半径缩放（这是现有 `_unhandled_input` 的 wheel 分支）。

### 10.3 交互状态机

```
SETTLED --wheel/drag--> DRAGGING --release(v>1.2 行/秒)--> MOMENTUM --减到 0--> SNAPPING --> SETTLED
                       |release(v<=1.2)--> SNAPPING
SNAPPING --spring 未稳--> SNAPPING --稳(sigma<0.01)--> SETTLED
任意编辑状态 --值变化--> EDIT_PENDING --CONFIRM--> CONFIRMING --> SETTLED
真实模式：所有状态被 set_editable(false) 冻结，仅 SETTLED
```

- 数值模型：`row_h=28`，可见 5 行，中心行为选中值；`scroll` 为浮点行偏移。弹簧 `ω=18, ζ=1`（临界阻尼），吸附 0.25—0.35 s 稳定；惯性 `v>1.2 行/秒` 进入 MOMENTUM，摩擦 `exp(-6dt)`；速度用 60—80 ms 的 EMA（.35）估计，避免抖动。
- 滚轮一格 = 1 行 = 1 单位（年/月/日/时/分各自）。
- 拖动：`scroll -= dy/row_h`，松手按速度决定吸附/惯性。
- 年份 1..9999 **不循环**（钳制 + 边缘回弹 0.25 行）；月/时/分循环；日按 `isle_calendar.days_in_month(y,m)` 钳制。
- 吸附结束后 `parts_changed` 只发一次，避免每帧触发外部重算。

## 11. 分阶段开发顺序、文件范围、测试与验收门（任务书 §8/§9 对应）

### 11.1 顺序决策

任务书建议顺序为 -01 调研 → -02 冬季树/栖点/红花 → -03 白化 → -04 天气权重与 windy 合并 → -05 强风视觉 → -06 照明 → -07 滚轮 → -08 集成回归冻结。经依赖分析，**主顺序保持建议顺序**，但补充三条硬/软依赖与一条并行建议：

| 关系 | 性质 | 说明 |
|------|------|------|
| -04 → -05 | **硬依赖** | -05 的验收前提是“strong_wind 是唯一具名强风”，若 windy 仍在，强风落叶/秋千验收会被“普通有风也吹”污染 |
| -02 → -03 | 软依赖 | -03 的冬季截图需先消除浮空树冠，否则白化截图仍带 4 个悬浮绿球；且 -02 建立的季节生态快照（`_eco_ctx` season 字段）可被 -03 复用 |
| -03 → -06 | 软依赖（避免冲突） | 两者都改 toon.gdshader 与 main.gd 共享 uniform 区，串行减少 rebase；-06 的室内外体积掩码与 -03 的 `indoor_mask()` 是同一套 `g_house` 数据，建议 -03 先落地数据与函数，-06 复用 |
| -07 与 -05/-06 | 可并行（可选） | -07 只碰 hud.gd + 新文件 ui_datetime_wheel.gd，与 shader/场景无关；若用独立 worktree，可由第二位开发者并行 |

**最终建议**：-02 → -03 → -04 → -05 → -06 → -07 → -08，-07 可选并行。不建议把 -06 提前到 -03 之前（会与白化的 shader 改动冲突，且 -06 的室内外掩码依赖 -03 的 `g_house` 数据）；不建议把 -04 放到 -05 之后（语义矛盾）。

## 12. 回滚方案、潜在冲突与未解决问题（任务书 §8.12 对应）

### 12.1 回滚策略

1. **每阶段独立分支 + 冻结 tag**：`p81-02-winter-trees`、`p81-03-whiteness`、`p81-04-weather-weights`、`p81-05-wind-visuals`、`p81-06-lighting`、`p81-07-wheel`，验收通过才合入 `p81-integration`；失败则 `git branch -D` 或 revert 单 merge commit。基线始终为 tag `p8-weather-seasons-freeze-20261022`。
2. **Shader 默认值即回滚开关**：新增 uniform 全部默认“旧外观”（`g_winter=0`、`g_linfo` 全 0 时等价于现 12 槽行为、`snow` 块乘 `(1-indoor)` 在旧行为下无影响），因此**不改逻辑、只把 uniform 清零即可视觉回滚**，便于 A/B 截图与线上问题定位。
3. **设置项迁移可逆**：windy→strong_wind 迁移只写新值；旧版本存档回滚到 P8 代码时，strong_wind 在旧 13 类里已存在，不会崩；但旧版把 strong_wind 当普通类型，概率表不同——回滚说明写入发布说明。
4. **发布包**：-08 才重建 exe；若 -08 失败，发布目录仍保留 P7-V3.1 exe（当前状态），并明确标注“P8/P8.1 未发布”。
5. **数据产物**：`开发产物/p81/` 全部为新增，不受回滚影响；`docs/P8_1_REFINEMENT_PLAN.md` 本身是交付物，不随代码回滚删除。
